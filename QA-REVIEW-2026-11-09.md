# Normal-user app review — 2026-11-09

**Review status:** Browser audit recorded; developer review and acceptance pending. No application fixes were made. This is broad coverage of the reachable user interface, not a claim that every possible state or browser has been tested.

**Follow-up:** All seven findings have implementation fixes and local verification recorded in [the fix evidence](qa-review-2026-11-09/fixes/README.md). Developer confirmation remains pending. The original observations below are retained as the audit baseline.

## Environment and method

- Checkout: `0c86a14` (`test: evaluate integrated recommendation renewal`). The pre-existing untracked `Residue Recommendations based on benchmarks` file was preserved.
- App: actual local live runtime at `http://localhost:5080`, started with `bash scripts/run_live.sh`. Existing private configuration and live providers were used. No fixture provider, synthetic music, direct database edits, or mocked successful recommendations.
- Browsers: Obscura MCP and Playwright MCP, started as temporary stdio sessions through a local MCP client. Obscura required `OBSCURA_ALLOW_PRIVATE_NETWORK=1`; Playwright used installed `/usr/bin/chromium-browser` with a fresh profile. Default Obscura blocked localhost; default Playwright expected missing `/opt/google/chrome/chrome`. No persistent MCP configuration was changed.
- Actions used the rendered UI, accessible roles, keyboard controls, and ordinary links. DOM/console/network inspection supplemented those actions. Exports were downloaded through the UI. Browser contexts were isolated for ownership checks.
- Two disposable accounts were created. Account discovery produced two batches of five picks; guest discovery produced one batch of two picks. Both accounts were deleted afterward. Saved test guest data was cleared. Public catalog/cache effects of real searches and generation can remain under normal retention.
- Desktop views plus 390px mobile views were reviewed visually. Taste layout was also measured at 768px and 1440px. Screenshots and concise results are in [qa-review-2026-11-09/evidence](qa-review-2026-11-09/evidence/).

## Findings for later review

### 1. Familiar recordings are difficult to find — medium, observed

**Steps:** Your taste → Music type → Tracks → enter `Paranoid Android` → Search music source.

**Observed:** Ten results were cover recordings, including Martin Valcke, The Beelzebubs, Rockabye Baby!, and Easy Star All-Stars. The Radiohead recording did not appear. Refining the query to `Paranoid Android Radiohead` returned “The source found no matches. Try another spelling.” There was no visible next-page control. This prevented selecting the intended favorite through these two ordinary searches.

Album lookup for `OK Computer` did find Radiohead, although a Lemaitre release appeared first. A later local `Radiohead` keyboard selection chose the separately labeled `radiohead 3` artist. Labels distinguish these identities, but users must inspect results closely; matching a familiar title/name does not reliably put the intended entity first.

**Expected:** A practical way to find the intended recording and refine by artist, with useful ordering or continuation when covers fill the first page. Upstream indexing and query construction have not been distinguished as causes.

Evidence: [track search](qa-review-2026-11-09/evidence/track-search-covers.png), [refined query](qa-review-2026-11-09/evidence/track-refined-no-match.png), [keyboard selection](qa-review-2026-11-09/evidence/keyboard-new-artist-checks.txt).

### 2. Artwork repeatedly fails; artist fallback is poorly rendered — medium, observed

**Steps:** Add Radiohead as an artist favorite; save, reload, and browse between taste and discovery/history.

**Observed:** `/api/artwork/artists/a74b1b7f-71a5-4011-9441-d0b5e4122711` repeatedly returned HTTP 503. The circular fallback showed a small, partly clipped `R` near its upper-left edge. Some recommendation cover requests also failed, leaving placeholders. Some album artwork loaded correctly earlier in the same journey.

A console snapshot taken before the final keyboard checks contained 104 artist-artwork failures and 34 other artwork failures across repeated navigation, reloads, and generation polling. These are cumulative observations, not a per-minute rate or a count of unique images. They do not establish whether the cause is upstream availability, local storage/cache policy, or browser retries.

**Expected:** A legible, centered fallback; failures should not produce excessive repeated requests. Investigate the failed response lifecycle before changing providers or caching policy.

Evidence: [mobile taste](qa-review-2026-11-09/evidence/mobile-taste.png), [mobile discovery](qa-review-2026-11-09/evidence/mobile-discover.png), [desktop taste](qa-review-2026-11-09/evidence/taste-desktop.png).

### 3. Existing recommendations appear beneath the updated taste — medium, observed UX ambiguity

**Steps:** Generate the Radiohead/rock batch; edit taste to include the selected track and jazz; save without generating; return to Discover.

**Observed:** “Based on your taste” showed the updated Radiohead / Paranoid Android / jazz profile, while the existing five picks and stored explanations still described the earlier rock-based generation. The batch was correctly retained, but the screen did not make this difference in timing clear.

**Expected:** Identify the taste used for the displayed batch, or explicitly distinguish current preferences for the next request from the taste used previously. This finding concerns presentation; it does not prove that stored scoring evidence changed.

Evidence: [updated taste and existing batch](qa-review-2026-11-09/evidence/mobile-discover.png), [saved updated preferences](qa-review-2026-11-09/evidence/mobile-taste.png).

### 4. Empty catalog-search message appears twice — low, observed

**Steps:** On Your taste, search for an artist absent from the local catalog, before choosing Search music source. This occurred during the initial `Radiohead` search.

**Observed:** The visible page text repeated “No local matches. You can search the music source explicitly.” twice, followed by Search music source and Close results.

**Expected:** One clear empty-state message. The exact rendered placement and screen-reader announcement behavior still need targeted inspection; this is not an established accessibility violation.

### 5. Track subtitle repeats the same album title — low, observed

**Steps:** Select the Rockabye Baby! recording of `Paranoid Android`, save, and reload Your taste.

**Observed:** The row displayed `Lullaby Renditions of Radiohead · Lullaby Renditions of Radiohead`. On mobile the duplicate consumes several lines.

**Expected:** Collapse identical album/release labels while retaining meaningful differences.

Evidence: [mobile taste](qa-review-2026-11-09/evidence/mobile-taste.png).

### 6. Feedback transition with an existing rating needs targeted reproduction — medium, unresolved observation

**Sequence:** Like the first pick; save rating 8/10 and a Unicode note; reload; choose Already know; then choose Not for me, using approximately 700ms waits between feedback actions.

**Observed once:** Already know became selected, but Not for me remained unselected. The console included a feedback HTTP 400. Clearing feedback then succeeded. A later sequence of Like → Already know → Not for me, after clearing the rating/note and waiting 2.5 seconds between actions, saved and persisted correctly.

**Follow-up:** Repeat the original rated/note-bearing sequence and distinguish conflicting retained rating data from an in-flight save race. The slower successful test does not isolate those variables. Do not treat the failed transition as disproved or as a confirmed general feedback failure.

Evidence: [initial sequence](qa-review-2026-11-09/evidence/feedback-checks.txt), [successful unrated sequence](qa-review-2026-11-09/evidence/feedback-transition-checks.txt).

### 7. Browser favicon request returns 404 — low, observed

Opening the app caused `GET /favicon.ico` → 404. Verify the intended favicon declarations/assets and browser fallback behavior.

## Tool observations and limits

Obscura executed guest tag saving, live generation, account claim, sign-out and sign-in, history navigation, and DOM inspection. Its screenshot renderer differed visibly from Chromium: tags wrapped unusually and controls/shadows looked different. [Obscura screenshot](qa-review-2026-11-09/evidence/obscura-taste-renderer.png) is retained as tool evidence, not a confirmed Chromium product defect. Playwright Chromium screenshots were the primary visual reference. Some full-page captures include sticky-header/focus artifacts; do not classify those from screenshots alone.

The first axe script-tag injection was blocked by the app’s CSP. The successful scan evaluated the same installed axe source through Playwright without changing the application’s CSP. That deliberate failed injection contributed one console error and is excluded from product findings. Invalid-login and isolated-session 401s were expected. Build emitted dependency-pruning and StringTools target-framework warnings; dependencies were not changed in this audit.

Not covered: public deployment/TLS, real email delivery or unsubscribe delivery, seven-day expiry passage, ten-session history limits, provider outages/rate-limit exhaustion, every preference combination, Last.fm/ListenBrainz account import not exposed in the exercised UI, every search language/entity, real audio playback, listening-based recommendation quality, Firefox/Safari, physical devices, full screen-reader use, or a comprehensive security/privacy/storage audit. An artist-source lookup exceeded a 30-second automation wait before results eventually appeared; consistent latency was not measured.

No scorer, application source, dependencies, migrations, or production settings were modified. Raw exports and generated credentials were kept out of the committed report. Developer review should prioritize findings 1–3 and reproduce finding 6 with the original rating/note state.
